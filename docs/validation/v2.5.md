# v2.5 validation record

Target version: 2.5.0. Validation date: 2026-11-21. This record covers the 2.5
series, which adds reMarkable OS 3.29.x on the Paper Pro and reMarkable 2.

## Device under test

reMarkable Paper Pro (`reMarkable Ferrari`), aarch64, reMarkable OS 3.29.1.0
(Codex Linux 6.0.112, kernel `6.12.49+git-imx8mm-ferrari-geadc2c7b4701`,
Qt 6.10.3), connected over USB. Xochitl SHA-256
`35e940d8acb3de0dfaf61f1a421d450e61dbaa915f885c818a2a3cc5c94c8ecd`. The tablet
started clean: Developer Mode on, no XOVI, no AppLoad, no hashtable.

Runtime: XOVI 0.3.3 and rm-xovi-extensions release 19 (unchanged from 2.4),
AppLoad 0.6.0 (`appload.so` SHA-256
`5b2dd6c066da6932d88a1d62be1068ca5ba751f481636dd51f727221db62e3ad`; the release
tarballs match Vellum's SHA-512 values for `appload` 0.6.0).

## Why 3.29 needed more than a wider firmware window

- AppLoad 0.5.3 hooks the pre-3.28 Xochitl interface; 3.29 needs AppLoad 0.6.0.
  0.6.0 in turn does not hook 3.27, so the release carries both.
- Starting XOVI with no hashtable built on the running firmware made
  qt-resource-rebuilder abort Xochitl (`Couldn't resolve the hashed identifier
  … required by AppLoad hooks in main UI`). systemd restarted it four times and
  `rm-emergency.service` rebooted the tablet. `rm-emergency.sh` also falls back
  to the previous OS partition when an update has just been applied, so the
  same crash right after an OS update would roll the tablet back.
- Earlier releases never built the hashtable, and their success check (an
  `LD_PRELOAD` entry in Xochitl's environment) also passes for a Xochitl that is
  about to abort.

## Device validation (Paper Pro, 3.29.1.0)

The device steps were run over SSH exactly as the installer runs them: the
payload files the installer uploads for this device (aarch64, AppLoad 0.6.0
only) staged in `/tmp/trmnl-install`, then
`/bin/sh /tmp/trmnl-install/install-device-runtime.sh`. The Windows installer
itself was not driven: it authenticates with the SSH password only, and the
password available for this run was rejected by the tablet.

Device archive under test (aarch64, built from this tree on macOS with the same
steps as `build.ps1`/`build-release.ps1`): SHA-256
`a253b82ceebcf59c81191d3732fc867c902a3bef9a6151b727fb06273f67860d`. The signed
Windows release ZIP has not been built or exercised; its SHA-256 belongs here
once it has.

Found and fixed during the run:

- Reinstalling while XOVI was active, the start check took the already-injected
  Xochitl for the new one and then reported its replacement as a crash. It now
  waits for a process that replaced the previous one.
- A crash at start reached the emergency reboot after a single retry: XOVI
  re-mounting an unchanged drop-in does not reset systemd's start-rate count
  (four starts in ten minutes), so earlier activations had used it up.
  `activate.sh` now runs `systemctl reset-failed xochitl` before starting and
  polls every quarter second, stopping Xochitl at the first restart.
- The runtime installer copied `appload.so` and the shims over the files Xochitl
  had mapped. It now copies beside them and renames into place.

## Not covered

- reMarkable 2 on 3.29: allowed by the installer with the arm32 AppLoad 0.6.0
  build, not exercised on hardware.
- 3.26.x and 3.27.x with this release: the AppLoad 0.5.3 path is unchanged
  apart from `activate.sh`, but was not re-run on hardware.
- 3.28.x: AppLoad 0.6.0 supports it, and the installer still refuses it.
- A real TRMNL cloud Device API refresh: only the mock was used.
- Reboot to stock and reactivation after a reboot. The tablet rebooted twice
  during the run (both times from a deliberate or accidental crash loop) and
  came back to stock; reactivation afterwards passed.
